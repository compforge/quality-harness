# Trace Harness：Batch 分析

本文设计 Python Trace Harness 的多条 trace 统计与对比，回答“一类问题有多普遍”和“改动后是否改善”。
通用概念和职责边界见 [Trace Harness](../../../../docs/trace-harness.md)。
单条建模、度量和判读沿用 [单条分析设计](single.md)，共同语义遵守
[Kernel](../../../../docs/kernel.md#dataset-与反复评估)。未来 trajectory 批量分析复用适用的执行机制，
保留各自的领域模型。

**状态：现有 corpus 已有离线批量分析和表上算子；本文的数据集冻结、有界执行、Measurement
落表及完整对比流程是待实现设计，不代表现有 CLI 已支持。** 本文不新增公共 API 或 schema 契约。

## 1. 现有能力与缺口

| 现有入口 | 已有能力 | 对本设计的限制 |
| --- | --- | --- |
| `Cohort.of / select` | 单条采集、查询命中 span、按 trace 建模、过滤及分布对比 | 保存整批 contexts；命中子集可能缺关联 span |
| `corpus.experiment` | 从离线 Jaeger 文件批量分析，输出表、报告与 Verdict，可读基线进行 diff | 先累积 contexts，再构建整批表；不等于完整在线实验编排 |
| `CorpusTables` | traces / facts / findings 三表，支持 Parquet，缺可选依赖时回退 JSONL | 表本身仍是内存列表，尚未承载独立 Measurement 结果 |
| corpus 算子 | error_signature、fleet_outlier、contrast、diff、pattern_rates | 不能据已有对比函数推断采样、缺失值或统计置信度已完整处理 |

因此问题不只是“要不要建树”。原始属性、整批 contexts、重复物化的行以及聚合状态都可能
随数据量增长。只去掉 tree，不改变对象生命周期，仍然可能耗尽内存。

## 2. 概念与职责

| 词汇 | 本设计中的含义 |
| --- | --- |
| Dataset | 固定版本的 Unit facts 与证据来源，代表可复用的一批输入 |
| Filter / Slice | 从 Dataset 选择可解释的子集，保留筛选条件与父 Dataset 身份 |
| EvaluationRun | 对确定 Dataset version 执行所选分析；面向使用者可称分析运行 |
| Worksheet | 与 Dataset 相同粒度的行及本轮 Measurement、Finding、状态 |
| Summary / Aggregation | 从本轮行结果生成计数、分布、出现率等摘要 |
| Comparison | baseline 与 candidate 两份分析结果的对比 |
| Batch | 执行方式，不额外承担数据集或结果身份 |

`Cohort` 可以保留为现有接口名称，不再用它同时解释数据集、执行器与结果。
对已有线上 trace 的分析是 Analytics；固定输入、改变版本或配置并主动重跑才适合称为
Experiment。两者可以共享分析组件，但采样和证据强度不同。

### 数据、结果与粒度

Dataset 固定输入，不收纳某轮 Finding 或 Measurement。更换规则、阈值或 measurer 创建新的
EvaluationRun；补入缺失 span、改变事实投影或输入样本形成新的 Dataset version。
仅记录 trace_id 不能保证复现：遥测可能过期或晚到，需要保存输入快照，或引用可验证的不可变
存储对象及内容摘要，同时记录采集条件、采样方式、时间范围和完整性。

一个 Worksheet 只对应一种 Unit grain：

| 粒度 | 稳定身份 | 适合回答的问题 |
| --- | --- | --- |
| 逻辑调用 / node | trace_id + node_id | 某 API 调用耗时与慢调用比例 |
| 请求 | 消费方定义的 request key，保留 trace 和锚点关联 | 用户等待时间、每请求调用量、受影响请求比例 |
| trace | trace_id | 链路整体覆盖范围与 trace 级模式 |
| trajectory | trajectory SDK 定义的 trajectory key | 轨迹效果、成本、轮数与行为模式 |

一个 trace 不一定等于一个请求。调用次数多的请求也不能在用户等待时间分布中获得更多权重。
Measurement 可以有多个维度，但这些维度不能改变所属 Unit 的身份和聚合分母。

## 3. 处理流程与内存边界

```text
确定样本总体与采样策略
  → 固定 Dataset 输入、来源及完整性
  → 分页读取 / 调度有限数量的 trace
  → 根据所选指标准备字段和必要关系
  → 复用单条 transform / measure / diagnose
  → 分批写 Worksheet 结果，释放原文、Node 和关系索引
  → 对结果表聚合、对比，输出摘要与证据入口
  → 按 trace_id / node_id 下钻到单条报告
```

首先采用**逐条或小批分析、落盘、释放上下文**，复用已有建模和分析入口，不先另造一套
轻量分析引擎。batch 执行必须接受与 single 相同的 scoped contributions，不能隐式退回默认
specs 或丢失业务 measurer / detector。Parquet 或 JSONL 是存储选择，不自动提供有界内存。

### 按指标选择最小充分输入

字段投影与关系完整性是两个独立维度。执行所需输入由指标契约决定，不能将“只保留查询
命中的 span”当成所有指标都有效的 light 模式。

| 指标需求 | 最小输入 | 执行选择 |
| --- | --- | --- |
| 某侧物理 HTTP span 的 duration、状态计数 | 对应物理 span 的必需字段 | 可以仅做归一与列投影，明确为物理 span 口径 |
| 逻辑调用数、client/server 去重 | 配对证据和所需关系 | 复用逻辑建模，不能简单按 span 数求和 |
| 同 API 连续串行调用 | 同一比较范围的完整有序调用集合、API 身份和时间区间 | 补齐局部关系；过滤掉中间调用后不可判“连续” |
| self、请求前缀覆盖、阶段完成耗时 | 请求/阶段锚点及覆盖该范围的相关调用和拓扑 | 必要时获取完整 trace 并运行单条分析 |
| 结构解释、原文检查、AgentRun 提取 | 对应完整关系及按需原文 | 下钻时补充；如属于全量指标，则对全部适用样本执行 |

建模不是全有或全无的选择。纯列计算可以有 fast path，但需在 profiling 证明收益后引入，
并与单条实现共享归一化规则、保持语义等价。即便需要完整 Node 集，也只在受控数量的 trace
上保留，通常无需创建 DisplayNode、HTML 或全部 prompt 文本。

只对慢样本深查可以解释慢样本，不能将其指标分布标成全部请求的分布。每个指标都记录适用
范围和有效样本数；输入不足则留下未计算原因，不能静默用子集算出的结果代替完整结果。

### 有界执行

- 分页采集、按 trace 去重，明确后端 span limit 与目标 trace 数的区别。长 trace 跨页时不能
  在第一页就认定采集完成；查询截断必须可见。
- 设置同时处理的 trace 数、在途字节与单 trace 大小预算。队列采用背压，按需批量获取减少
  HTTP 往返；并发提高前先遵守后端容量、统一 client 和连接池配置。
- 结果分批写入后释放上下文，不把已完成的 ctx 保存在结果对象中。重试与续跑按 Unit key
  去重，避免重复计数；结果写入完成后再更新进度，保留部分运行状态。
- 聚合也需限制状态：高基数 group-by 可分区落盘，精确分位数可外部排序，近似分位数使用
  可合并的有界摘要并声明精度。不能先将全量结果重新加载成一个 DataFrame。
- 超大 trace 超出资源预算时记录资源失败及受影响指标；不能静默截断后输出正常结果。

目标内存随读取页大小、有限在途 trace 体积和聚合预算增长，不随 Dataset 总 trace 数增长。
吞吐瓶颈可能在取数、解析或度量，需要分别记录耗时、字节、调用量和峰值内存后再优化。

## 4. 度量、告警与聚合口径

结果表保留 Unit key、指标与规则版本、单位、维度、计算状态和证据引用。
每个指标分别记录总体数、适用数、有效数、缺失/失败数以及排除原因。业务失败、取消和超时
也要统计；只统计成功请求的耗时需明确标注，不能以更高错误率换取看似更低的延迟。

基础摘要包括 n、p50 / p90 / p95、慢请求率、错误率和代表样本。分位数从整体有效样本或
可合并摘要计算，不能平均各批次的 p95。字段单位与指标定义不一致时拒绝直接比较。

### 时间口径

同一逻辑 HTTP 调用不能重复计入 client 与 server 两份时长；调用侧与服务侧也不能混在同一
分布。duration sum、区间并集覆盖时间和请求 wall-clock 是不同指标。嵌套或并行时长不可
相加作为请求耗时；`self_ms` 或未覆盖区间只表示缺少子调用覆盖，不能自动归因为连接初始化。

跨主机时间戳可能有偏差，阶段间隔和串行判定应保留时钟质量限制。trace 父子关系本身不等于
完整因果图，关键路径分析需要额外的因果和等待关系，不能简单选择最慢的子节点。

### warn detector 的批量统计

单条 detector 解释实例，批量分析统计其发生频率。以当前需求为例：

| 检测项 | 单条证据 | 批量统计 |
| --- | --- | --- |
| 普通 HTTP 单次超过 200 ms | 调用侧、归一 API、耗时、node/span | 慢调用数 / 有效调用数；受影响请求数 / 有效请求数 |
| 多次连续串行调用相同 API | 同一范围内的有序调用、区间、间隔及重复次数 | 命中请求比例、连续次数分布、相关覆盖时间 |
| 意图识别模型开启 thinking | 业务阶段识别与显式模型配置 | 开启比例，并按配置切片比较阶段耗时 |

200 ms、普通 HTTP 的适用范围、连续次数阈值、API 归一规则和阶段识别由消费方配置或贡献，
不是 batch 引擎的通用业务常量。API 身份通常需要 method 和归一路由；同 API 不等于相同参数，
也不能据此直接判断调用可以合并或缓存。streaming、模型请求等应声明各自的指标适用范围。

出现率依赖完整计数，不能统计 Markdown、HTML、top-N 或受 detector 输出上限截断的 Finding。
若现有 detector 只返回样例，需要独立完整计数或 Measurement；样例数量与命中总量分别保存。
未运行的规则不能当作零命中，未采集 thinking 配置不能当作关闭。

## 5. Baseline 与 candidate 对比

对比绑定两个 Dataset version 和对应 EvaluationRun。规则或指标版本不同时，优先使用相同
配置重评两份固定输入，避免把分析器变化当成服务改进。

样本从声明的请求总体采集，不能仅选错误或慢 trace。记录遥测采样策略；若只能取得 tail-sampled
慢请求，报告结论限定于该样本总体，不能外推全部请求的慢请求率。

版本按目标服务的实际 revision、镜像或可验证部署信息归属。滚动发布期间，时间窗口本身不能
区分旧版与新版。每组同时保留环境、路由/策略、模型配置、输入规模及可取得的冷暖状态等维度，
对可比 Slice 展示差异，避免流量结构变化掩盖实际变化。

Comparison 展示 baseline / candidate 的样本数、覆盖率、分位数、绝对差和相对差、错误率及
warn 命中率，并链接代表 trace。baseline 为零时不生成无意义的百分比变化。摘要必须带口径，
不能只给一个“提升 X%”。

### memory KB client 复用的验证示例

以下是消费方分析配置的示例，不把 AS 业务名写进通用引擎：

1. 固定改动前后的可比样本，baseline 已包含相同的 Control client 优化，candidate 增加 KB
   client 复用，避免把两项改动的收益混在一起。
2. 以请求开始到意图识别结束为主要阶段指标。它是首次响应等待的代理指标；真正首次可见
   token 需有独立事件，不将二者等同。
3. 同时度量 memory 父操作耗时、KB 调用侧耗时与次数、调用前及子区间未覆盖时间，以及
   Control 的重复串行调用、错误和超时。
4. 按输入规模、检索策略、rerank / 模型 thinking 配置及版本切片，比较请求级分布与调用级分布。
   客户端初始化可能在 HTTP span 之外，单看 HTTP p95 可能漏掉收益；未覆盖时间下降仍需
   源码、补充埋点或受控实验才能归因到初始化。

自然流量前后对比说明关联。固定 Case、控制数据状态并交错重复运行两个版本，能提供更强的
改动证据；缓存与下游负载仍需考虑。若给出置信区间，应以请求等独立单元采样，重复调用按请求
聚类，配对实验按 pair 处理，不能把同一 trace 内的 span 当成独立样本夸大置信度。

Finding 不自动产生 Verdict。显式 Policy / gate 可以判断改善、回归或证据不足，但应包含
样本量、数据覆盖和可比性要求。现有 experiment 无 gates 时的 `skipped` 行为继续遵守共享契约。

## 6. 报告、下钻与 trajectory 边界

报告从持久化行结果生成，保留输入版本、运行配置、采集/分析失败数和统计口径。
优先呈现分布、版本差异、错误签名、模式出现率及代表样本；完整 Node / 原文证据通过稳定
身份下钻，避免将每条 trace 的整棵树嵌入 batch 报告。

错误签名聚类、同类调用离群、行为模式出现率是不同分析侧重点。某模式在失败样本中更常见
可以形成待验证假设，不自动证明工具描述、prompt 或某个参数是根因。

Trace 与 trajectory 可以共享固定数据集引用、有限并发、分批写入、进度、结果聚合和对比机制；
只有两个领域确有相同需求时才抽入中立共享层。Trace 继续拥有 span / Node / 调用关系，
Trajectory 继续拥有 turn / action / observation 和评估规则。
跨领域通过 Case、request、trace 或 trajectory 的明确关联键连接证据，保留一对多关系；
不能用一个 SDK import 另一个来拼装批量执行。

## 7. 实现验证边界

后续实现需验证以下性质，而非仅证明报告能够生成：

- 同一份输入与配置，single 和 batch 的 Measurement、Finding 语义一致；批量分片和并发不改变结果。
- client/server 配对、并行调用、跨窗口调用、缺失 span、连续调用被其他调用打断等案例保持正确口径。
- 倍增 trace 总量时，在途数据与峰值内存保持受预算约束；超大单 trace 和高基数聚合有明确处理结果。
- 分页、重试、续跑没有丢失或重复 Unit；缺失数据、截断和输出上限不会制造零告警或虚假的改善。
